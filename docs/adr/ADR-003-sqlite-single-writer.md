# ADR-003：项目 SQLite 唯一写入者

> 状态：已决策，M1 实现  
> 日期：2026-07-25  
> 关联计划：M1-03、M1-04、M1-05、M1-08

## 背景

应用有三层（React / Rust / Python）。若多语言同时写同一 SQLite 文件，会出现：

- 迁移与 schema 版本分裂
- 锁竞争与难排查的 `database is locked`
- 事务边界不清晰（尤其是“文件落盘 + 登记资产”）

需要明确谁持有写权限，以及全局库与项目库如何分工。

## 决策

1. **Python sidecar 是 `project.db` 与 `global.db` 的唯一写入者**  
   Rust / React **不得**直接 `sqlite3_open` 项目库。
2. **双库**：
   - `global.db`：最近项目、设备设置、适配器发现、组件状态、全局素材索引、Creative Pack 注册表
   - `project.db`：领域业务表（故事、事件、镜头、资产、任务、生成运行记录等）
3. **连接策略**：
   - 启用外键与 **WAL**
   - 合理 `busy_timeout`
   - 单 sidecar 进程内连接池；写事务串行，读可有限并发
   - 不在重型媒体任务热路径强制 checkpoint
4. **迁移**：
   - 打开项目时读 schema 版本
   - 迁移前轻量快照
   - 失败回滚并保持旧库可用
   - 旧应用打开新 schema：只读提示，不写
5. **访问面**：只通过领域命令 / 仓储 RPC，不暴露任意 SQL 给前端
6. **路径**：库中只存项目相对路径（配合 ADR-005）

## 证据与依据

- 架构文档 §9 已规定唯一写入者与 WAL（设计基线）
- M0 未实现持久化；M1 以此 ADR 为实现约束
- ADR-001 保证 UI 经 Rust 代理到 Python，天然适合集中写库

## 替代方案

### Rust 写库、Python 只做算子

减少跨语言往返，但领域模型与迁移会在 Rust 复制一套，AI 流水线状态仍在 Python。复杂度更高。不采用。

### 每层各写各的表

短期快，长期一致性与迁移灾难。禁止。

### 嵌入式其他数据库（例如 LiteFS / PostgreSQL 本机）

运维过重，单机桌面无收益。不采用。

## 影响

- 所有“保存/提交/入队”必须是 sidecar 命令
- 前端状态是投影，不是事实源
- 写事务不得等待外部 CLI / 模型（先落盘再短事务登记）
- 后台 worker 与 RPC 共用同一写串行策略，避免双写通道

## 回退

若出现不可接受的写瓶颈：

1. 先拆 read model / 投影表  
2. 再评估“只读副本 + 通知”，仍保持单一写者  
3. 不开放第二写入进程  

## 后续验证（M1）

- 强制退出后已入队任务仍在  
- 迁移失败可回滚  
- 并发读 + 串行写压力测试
